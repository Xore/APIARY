# win11-sandbox stability investigation — 2026-08-05T213000Z (#502)

Investigating #502 (ProcMon CLI export hangs indefinitely) with real
hypervisor/libvirt access to `win11-sandbox`. Found and fixed a real,
separate, higher-impact bug along the way; the export issue itself is only
partially explained.

## Finding: implicit watchdog causes unprompted whole-VM resets

`win11-kvm.xml` declares no `<watchdog>` element. The live domain, once
started, showed one anyway: `<watchdog model='itco' action='reset'>`.
libvirt/QEMU on this host (libvirt 12.0.0, QEMU 10.2.1, `pc-q35-10.2`
machine type) auto-injects a default Intel TCO watchdog device when none is
explicitly configured.

Windows has no built-in driver to service an Intel TCO watchdog. Nothing in
the guest ever resets its countdown, so it fires on its own timeout and
hard-resets the entire VM, completely independent of anything happening
inside the guest.

**Reproduced twice, unprompted, with no ProcMon or other guest action
involved:** a freshly reverted golden-image clone stayed up only
~90-120 seconds before `virsh domstate` showed `shut off` and the VM had to
be restarted. Confirmed via `virsh screenshot` mid-event on one occurrence:
the guest was mid-boot again (a fresh "Welcome" login screen), not stuck or
crashed with a visible dialog.

## Fix and verification

Added `<watchdog model='itco' action='none'/>` explicitly to
`win11-kvm.xml` (present, but never triggers a reset). Verified live:

- Redefined the domain, reverted to a fresh golden-image clone.
- Monitored `virsh domstate` every 15-30s for 15+ continuous minutes
  (well past the ~90-120s window it previously failed inside) — stayed
  `running` throughout, confirmed via WinRM `LastBootUpTime` staying
  constant across checks.
- Ran a real ProcMon start (`/AcceptEula /Quiet /BackingFile ...`) → wait →
  stop (`Stop-Process -Force`, matching `run_sample.py`'s current
  `stop_procmon()`) → CLI export (`/OpenLog ... /SaveAs ... /Quiet`) cycle
  through this same window. The VM did not reboot at any point during it.

## What this does and doesn't explain about #502

A silent, periodic whole-VM reset happening mid-operation looks exactly
like a hung remote command from the orchestrator's side: the WinRM
connection the Python script is waiting on just dies, with no error message
distinguishing "the guest rebooted" from "the remote process never
returned." This is very likely a real contributor to #502's reported
"hangs indefinitely" symptom, and fixing it removes a genuine, serious,
previously-undetected source of guest instability that would have affected
every long-running WinRM operation during a detonation, not just ProcMon's
export step.

**It is not the whole story.** With the watchdog neutralized and the VM
confirmed stable, a real ProcMon export of a ~15-20 second capture still
took roughly 200 seconds to complete (measured directly; a second, more
carefully isolated measurement was inconclusive because an earlier `taskkill`
issued to clean up a separate stray process may have interrupted it mid-run
rather than letting it finish on its own — needs a clean re-measurement).
200s for a tiny capture is still far slower than expected for what should be
a near-instant CSV dump, and #502's own original report already ruled out
"just needs more time" as the *sole* explanation (a tiny capture failed to
export within 300s in that report). Whether the export is genuinely slow
(some real bottleneck worth its own investigation) or was *also* still
intermittently affected by something else even with the watchdog fixed is
still open.

## Recommendation

Ship the watchdog fix now — it's a confirmed, real, high-value fix
independent of whatever else is going on with the export step specifically.
Leave #502 open for the export-speed question: next step should be a clean,
uninterrupted timing measurement (no manual process interference during the
wait) across a few repeated runs to see if ~200s is consistent, and whether
it scales with capture size or stays flat, before deciding if this needs a
longer timeout, a different invocation approach (issue's own untried
direction: the `Procmon.exe` bootstrap launcher instead of `Procmon64.exe`
directly, not yet tested), or a deeper look at what the export is actually
spending its time on.
