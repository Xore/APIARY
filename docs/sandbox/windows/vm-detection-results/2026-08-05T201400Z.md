# VM detection verification — 2026-08-05T201400Z (#368 remediation pass, item 2)

Follow-up to `2026-08-03T202426Z.md`'s item 2, which found `Win32_VideoController`
and `System.Windows.Forms.Screen` disagreeing on the same guest (`1280x800`
vs `1024x768`) and recommended re-checking via a real console/VNC session
rather than trusting either WinRM-only reading blindly.

## Fix

Added a `<resolution x='1920' y='1080'/>` hint to `win11-kvm.xml`'s VGA
`<model>` element (libvirt's supported way to set the QEMU stdvga device's
boot-time mode without switching away from plain VGA — the "not QXL, stealth"
choice documented alongside it is untouched):

```xml
<model type='vga' vram='16384' heads='1'>
  <resolution x='1920' y='1080'/>
</model>
```

## Verification

Redefined the domain, reverted to a fresh clone of the golden image (cold
boot, matching this issue's own established verification methodology), and
checked the resolution three independent ways:

1. **`virsh screenshot` (direct framebuffer capture, no guest agent
   involved)**: `1920x1080` — confirmed at the OVMF boot screen already,
   and again once the Windows desktop finished loading.
2. **`Get-CimInstance Win32_VideoController` over WinRM**:
   `CurrentHorizontalResolution=1920`, `CurrentVerticalResolution=1080` —
   matches the real framebuffer.
3. **`[System.Windows.Forms.Screen]::PrimaryScreen.Bounds` over WinRM**:
   still reads `1024x768` — same stale value as the prior report, on a
   guest now definitively confirmed (via two independent, non-WinRM-quirky
   methods) to actually be running at 1920x1080. This settles the prior
   report's open question: this specific API just doesn't reflect the real
   console resolution under a non-interactive WinRM session (no attached
   interactive desktop for `System.Windows.Forms` to query against), not a
   sign the guest itself is misconfigured. `verify_vm_detection.py`'s own
   `check_residual_tells()` uses exactly this API — its `screen_resolution`
   field will keep reading `1024x768` even though the real screen is
   correct; worth switching that check to `Win32_VideoController` in a
   follow-up so the automated report stops flagging a non-issue.

## Outcome

Item 2 (screen resolution) is resolved: the guest's actual display is
1920x1080, verified independent of the one WinRM API known to misreport it
under these conditions.
