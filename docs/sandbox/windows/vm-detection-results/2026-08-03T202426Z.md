## 2. Screen resolution — inconclusive, needs re-verification with a real session

`[System.Windows.Forms.Screen]::PrimaryScreen.Bounds` over a non-interactive
WinRM session reports `1024x768`. `Get-CimInstance Win32_VideoController`
(`CurrentHorizontalResolution`/`CurrentVerticalResolution`) reports
`1280x800` on the same guest, same session. Two different APIs disagreeing
on the same host suggests at least one of them is reporting a
session-specific virtual/default value rather than the guest's actual
console framebuffer resolution — WinRM's non-interactive shell may not have
a real desktop session attached for `System.Windows.Forms` to query
correctly. Neither number is the `1920x1080` target either way.

Not resolved this pass. `win11-kvm.xml` deliberately uses plain VGA (not
QXL/virtio-gpu) for stealth reasons already documented there; getting a
real 1920x1080 mode out of the Microsoft Basic Display Adapter driver
without a mode-setting driver or EDID injection needs its own investigation
— worth re-checking via an actual interactive/VNC session's reported
resolution (not WinRM) as the next step, per this issue's own item 4
guidance to re-verify rather than assume.

## 3. Bochs `SystemBiosVersion` / QEMU SCSI identifier — investigated, root cause found, not fixed this pass

**`SystemBiosVersion`**: `Win32_BIOS.Version` reads `"BOCHS  - 1"`, and
`HKLM\HARDWARE\DESCRIPTION\System\SystemBiosVersion` includes the string
`"Ubuntu distribution of EDK II - 10000"`. This is a *different* field from
the ones `win11-kvm.xml`'s `<sysinfo><bios>` block already successfully
overrides — `Win32_BIOS.Manufacturer` correctly reads `"American Megatrends
Inc."` and `SMBIOSBIOSVersion` correctly reads `"2.14.1"` on the same
guest. `SystemBiosVersion`/`Win32_BIOS.Version` appear to be populated from
OVMF's own embedded firmware build identification rather than the SMBIOS
Type 0 Vendor/Version/Date strings QEMU's `-smbios type=0` (and libvirt's
`<sysinfo>` wrapper around it) actually controls. This is firmware-binary
territory (OVMF's own build strings), not a libvirt XML or offline
registry fix — `HKLM\HARDWARE` is the volatile hardware hive, regenerated
fresh from ACPI/SMBIOS tables at every boot, so there's no persistent
registry value to edit offline either.

**QEMU SCSI identifier**: `Win32_DiskDrive.Model` reads `"QEMU HARDDISK"`,
`PNPDeviceID` includes `VEN_QEMU&PROD_HARDDISK`. The `SCSI\Disk...` PNP
class prefix itself is *not* a tell — Windows represents essentially all
block storage, including real SATA/AHCI disks, under the generic `SCSI`
device class, so that part is expected and not virtualization-specific.
The actual tell is the `QEMU`/`HARDDISK` vendor/product strings themselves,
which come from the ATA IDENTIFY DEVICE response QEMU's `ide-hd` backend
returns. `<disk><serial>` is already overridden correctly (`Win32_DiskDrive.
SerialNumber` reads the spoofed `WD-...` value) but libvirt's schema doesn't
expose an equivalent `<vendor>`/`<product>` override for `sata`-bus disks
the way it does for some `scsi`-bus device types; making QEMU report a
different ATA model string needs a lower-level `qemu:commandline` passthrough
or a different disk backend, not investigated further this pass.

Both explicitly accepted as known gaps for now, per this issue's own
acceptance-criteria language — not silently dropped, and not guessed at
with an unverified fix under time pressure. Worth a dedicated follow-up
issue with room to actually test OVMF firmware variables / qemu:commandline
options against a disposable clone before touching the real golden image.
